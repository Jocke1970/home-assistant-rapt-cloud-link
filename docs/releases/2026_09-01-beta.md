## Why this beta exists

BrewAssistant `v0.2.0-beta.12` requires the operational RAPT profile contract. The HA snapshot from 2026-09-19 exposed an active RAPT profile, profile session, seven steps and a 40°C Heatstrike target inside `sensor.rapt_cloud_link_brewzilla_debug`, but did not have an operational `binary_sensor` with `ba_source: rapt_cloud_link_brewzilla_profile_runtime`. That leaves BA's brewing source unselected and blocks BA writes as designed. The BA-specific `ba/brewassistant-rapt-cloud-link` branch contains the missing integration implementation; upstream-only `main` does not.

## Ownership and disconnected operation (mandatory contract)

- RCL can communicate with and control BrewZilla independently of BrewAssistant. The RAPT/BrewZilla profile runner is not dependent on BA being connected to RCL.
- While connected and authorized, BA computes/supervises hot-side decisions and sends all BrewZilla commands **through RCL-owned HA entities/services**. BA must not establish a parallel direct BrewZilla writer.
- **Loss of the BA–RCL connection, unavailable/stale RCL telemetry, an incomplete profile snapshot, or a transient step handoff is NOT a profile STOP.** BA must cease issuing new commands, invalidate pending BA actions, preserve RAPT session ownership and last-known context, and report control suspended / actual hardware state unknown. BA must NOT send heater OFF, pump OFF, zero utilization, end-profile, or any other actuator command solely because communication was lost. The RCL/BrewZilla process may continue independently.
- A STOP is a separate event requiring a fresh, explicit and verified RCL profile state transition. Never infer STOP from unavailable entities, a timeout, a restart, or a missing step. A deliberate operator ABORT is also a separate user-initiated event, not a connection-loss fallback; its semantics require independent testing.
- On reconnection, BA must refresh and reconcile the current RAPT session, step and target and invalidate stale approvals before permitting further supervised commands. Never replay queued actions from before the outage.
- RCL's independent operation does not establish that every kind of RCL-to-device outage can preserve control; distinguish BA–RCL loss from RCL–BrewZilla or RAPT Cloud loss. Hardware-safe shutdown must not be inferred from an HA switch state.

## Included

- Preserve all existing RCL BrewZilla, Pill, temperature, switch, number, bonded-device and diagnostic entities.
- Expose `BrewZilla Profile Active` as a binary sensor with stable `ba_source` marker and normalized profile/session/current-step/next-step/target fields. The actual HA entity ID depends on device naming; discover by marker instead of assuming `binary_sensor.brewzilla_profile_active`.
- Expose RCL start/end profile services. BA's physical BrewZilla command transport remains via RCL-owned Home Assistant number/switch entities, never a parallel direct BrewZilla client.
- Keep `profile_active: true` through an incomplete step handoff, while `profile_contract_complete: false` blocks positive BA commands when session ID, known step or its temperature target is missing.
- Match manifest to technical release tag; correct HACS README and add CI regression/Hassfest/HACS checks for release branches and tags.

## Install and acceptance — only after prerelease is published

1. Back up the existing RCL and HA configuration. Turn off BrewZilla heating and pump and check actual power/device state before replacing the integration. Do not perform changes during an active boil or heating run.
2. In HACS use **this fork** `https://github.com/Jocke1970/home-assistant-rapt-cloud-link`, not the original upstream URL; do not install two integrations with domain `rapt_cloud_link` side by side. Select the **published prerelease tag** `v0.5.0-beta.1`, not any development branch.
3. Restart HA with BrewZilla inactive; verify installed manifest version `0.5.0-beta.1` and RCL loaded without error. Existing entities must still be present.
4. Find binary sensor by its `ba_source` marker. Observe (without issuing heat/pump commands) `profile_active`, `profile_contract_complete`, `profile_session_id`, `step_id`, `step_name`, `step_target_temperature`, and `last_updated`. Compare its snapshot to the RCL BrewZilla debug sensor.
5. Only after the above: check BA source becomes `RAPT BrewZilla Profile`, runtime step and target match, and no stale queued actions appear. If the profile has stopped, confirm the source STOP guard and **physical output state separately**.
6. Before physical water testing, verify using mocks/read-only diagnostic evidence that BA–RCL loss causes **zero BA actuator/service calls**, that RAPT remains the selected owner, that a returned session is reconciled without replaying stale actions, and that real STOP/explicit ABORT remain distinct. In particular, fix/test BA beta.12's fixed-ID profile state-change listener against device-derived entity IDs in a separately versioned BA beta.
7. Physical water testing is *not* approved solely by this release: verify independent actual heat/pump feedback and the full installed-beta safety checklist first.

## Limitations / not claimed

- No physical testing is performed by CI, and a cloud API success or HA state is not proof of an electrically OFF heater.
- BA beta.12 has a fixed-ID RAPT profile state-change listener with a fallback for discovery. If HA creates a device-name-derived binary-sensor ID, source discovery can work but immediate STOP transition handling needs separate verification/fix in a new BA beta before heating. Do not bypass this gate.
- RAPT Cloud polling can be delayed; stale observations must suspend BA writes, not trigger BA-generated OFF commands.
- The published beta tag must point to the same SHA as the reviewed release branch and manifest; verify after publishing.
