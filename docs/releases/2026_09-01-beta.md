## Root cause

On 2026-09-19, RCL's debug entity included an active RAPT profile, session, seven steps and 40°C Heatstrike; the installed RCL did not expose the operational binary sensor (`ba_source: rapt_cloud_link_brewzilla_profile_runtime`) required by BrewAssistant beta.12. The BA-specific branch already contained it; upstream-only `main` did not.

## Autonomous ownership — hard rule

RCL/BrewZilla can continue a local profile without BA. BA sends ALL BrewZilla writes through RCL, never its own parallel direct writer. Missing/stale RCL telemetry, BA–RCL disconnection, incomplete profile data, a failed API poll or an intermediate step handoff is **not STOP**. BA must suspend new writes and pending approvals, preserve RAPT ownership and display physical outputs as unknown. It must NOT issue heater OFF, pump OFF, zero utilization, end-profile or any shutdown *because of link loss*. On reconnect, reconcile session/step/target and never replay queued actions. BA–RCL loss and RCL–device/cloud failure are different and independent hardware behavior must not be assumed.

An operator ABORT is a distinct explicit action. A profile STOP is separate from link loss and requires fresh evidence tied to the previously observed session. A cloud HTTP success or HA switch OFF is not evidence that outputs are physically OFF.

## Included in this RCL candidate

- Preserve all existing BrewZilla/Pill/temperature/bonded sensors, switch and number controls, diagnostics and RCL start/end profile services.
- Operational BrewZilla Profile Active binary sensor, discoverable by `ba_source`, with session, current and next step, and target. HA entity IDs may contain device naming, so do not assume a fixed ID.
- `profile_contract_complete` is false when session ID, recognized step or target is missing; preserve profile ownership during an incomplete step handoff.
- **Separate STOP attestation:** coordinator remembers an actual session ID from a successfully observed active profile. Only after **two consecutive successful, connected BrewZilla polls** showing no root or telemetry profile markers does it set `profile_stop_confirmed: true` and `profile_stopped_session_id` to that specific run. A failed poll, disconnected status, partial handoff, unknown session or cold-start OFF cannot attest STOP. This is cloud-level evidence, not independent physical proof.
- BrewZilla polling at most every 60 seconds while an active profile or an unverified potential STOP exists (respecting a faster operator setting); other RCL coordinators keep their configured cadence. If cloud observations become stale, BA suspends writes rather than sending OFF.
- Manifest/tag matching, corrected fork HACS URL, regression tests and intended Python/Hassfest/HACS checks.

1. Back up Home Assistant and the existing RCL integration. Stop heating and pumping deliberately using the approved controls, verify power/device state separately and never replace RCL during active heating.
2. Configure HACS to use this **fork** `https://github.com/Jocke1970/home-assistant-rapt-cloud-link` (Integration), not upstream. Both use domain `rapt_cloud_link`: never install duplicate integrations side-by-side or delete the existing HA config entry/credentials.
3. Select the **published** `v0.5.0-beta.1` prerelease, not the branch. Restart HA while BrewZilla is inactive; check installed manifest `0.5.0-beta.1` and existing sensors, switches and numbers.
4. Find the actual profile binary sensor by its `ba_source`, then validate active profile, contract, session ID, step ID, target and update timestamps against RCL debug. First missing profile observation after a known active run must have `profile_stop_confirmed: false`; two clean connected observations can attest it with the same session ID.
5. Use the separately published, corrected BA prerelease; validate source selection, accurate step/target, and **zero BA output commands on disconnect**, followed by reconciliation without queued command replay. Validate actual STOP and deliberate operator ABORT separately.
6. Practical water testing requires independent real heat/pump power and readback checks and explicit operator permission. CI, cloud data and accepted service calls alone cannot establish physical safety.

## Not claimed / limitations

- Neither integration can withdraw an already in-flight cloud command when connection disappears; the guard prevents subsequent commands, not a hardware emergency stop.
- Two clean cloud polls strengthen STOP evidence but do not prove electrical isolation or operation of a local hardware safety interlock.
- GitHub Actions/Hassfest/HACS are release gates. Do not publish while any gate is missing, failed or not tied to the intended SHA; confirm the final tag points to the exact reviewed manifest/source SHA.
